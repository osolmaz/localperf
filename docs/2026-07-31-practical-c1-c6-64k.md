# Practical c1/c6 64k

This sweep measures generation speed at the beginning and end of a 64k context window. It uses only concurrency 1 and concurrency 6.

## User instruction

The sweep was requested as:

```text
I want to create a new sort of sweep

c1, c6, both at 64k context, generate while context as full as possible and while context is empty

Im not interested in any other types of runs

where should i save this sweep now. it should be like a practical sweep
```

The built-in suite name is `practical-64k`.

## Fixed grid

Use one server profile with these limits:

| Setting | Value |
| --- | ---: |
| Context capacity | 65,536 tokens per sequence |
| Maximum concurrent sequences | 6 |
| Client concurrency | 1 and 6 |
| Repeats | 3 |
| Temperature | 0 |
| Forced output length | 1,024 tokens |
| Prefix caching | Disabled |

Run only these two workloads:

| Workload | Requested input | Requested output | Context meaning |
| --- | ---: | ---: | --- |
| `generate-empty` | Minimum valid prompt | 1,024 | Generation starts with the context as empty as the endpoint allows. |
| `generate-full` | Up to 64,512 | 1,024 | Generation ends as close as possible to 65,536 active tokens. |

A request cannot generate from literally zero tokens. For `generate-empty`, use the smallest prompt accepted by the tokenizer and endpoint, then store and report the measured prompt-token count.

For `generate-full`, start with 64,512 requested input tokens. Chat templates or tokenizer differences may add tokens. If the endpoint rejects that shape, reduce the input by the measured overhead and use the largest accepted value whose measured input plus 1,024 generated tokens does not exceed 65,536. Record both requested and measured counts.

## Measurement units

This fixed sweep uses one concurrent batch per repeat:

| Concurrency | Requests |
| ---: | ---: |
| 1 | 1 |
| 6 | 6 simultaneous distinct requests |

The suite declares the batches explicitly: one request at c1 and six requests
at c6. Keep all three repeats and treat the repeats as the independent
replication axis. Do not select the fastest repeat.

## Prompt and output rules

Use distinct prompts with different first cache blocks. Random request IDs alone do not prove that prompt text differs.

Force exactly 1,024 output tokens with deterministic sampling and EOS ignored. Reject early stops, missing usage counts, failed requests, cache reuse, or measured contexts outside the declared shape.

## Results

Every reportable point must show both decode and prefill results. This applies to
all four practical cases:

| Workload | c1 | c6 |
| --- | --- | --- |
| `generate-empty` | Decode and prefill | Decode and prefill |
| `generate-full` | Decode and prefill | Decode and prefill |

Both values come from the same streamed generation requests. Do not add a
prefill-only workload to this fixed grid.

The headline throughput table must retain the established pre-2026-07-31
LocalPerf columns, in this order:

1. `Users`
2. `Decode tok/s`
3. `Decode/user`
4. `Decode TTFT avg`
5. `Decode TTFT p99`
6. `Prefill tok/s`
7. `Prefill/user`
8. `Prefill TTFT avg`
9. `Prefill TTFT p99`
10. `OK / Err`
11. `SLO / goodput`, only when the workload declares an SLO

Do not add a separate full-run table or replace these headings with
`E2E output`, `output share`, `generation output`, `post-first-token`, or
`steady decode` headings.

Populate the columns as follows:

- `Decode tok/s`: aggregate generated output tokens divided by the complete
  measurement wall time.
- `Decode/user`: `Decode tok/s` divided by configured concurrency.
- `Decode TTFT avg` and `Decode TTFT p99`: streamed TTFT statistics.
- `Prefill tok/s`: aggregate effective prefill, using all prompt tokens divided
  by the time from the earliest request start to the latest streamed first
  token.
- `Prefill/user`: aggregate effective prefill divided by configured
  concurrency, preserving the historical `/user` column contract.
- `Prefill TTFT avg` and `Prefill TTFT p99`: the streamed TTFT statistics that
  bound the effective prefill measurement.
- `OK / Err`: completed and failed requests across all repeats represented by
  the row.

The `generate-empty` prompt is deliberately tiny, so its effective prefill
number is dominated by fixed request and scheduling overhead. Still report it,
because the practical sweep contract requires decode and prefill for every
case. Show the measured prompt-token shape and explain this limitation in the
row detail or legend. Do not relabel it as isolated kernel prefill throughput.

Keep TPOT, ITL, end-to-end latency, request-level distributions, exact prompt
and output counts, repeat spread, failures, runtime and backend identity, and
memory telemetry in the existing detail, repeat, and provenance sections. Do
not add any of them as a new headline column.

Store all runs for one model in one model-level SQLite artifact and render one
HTML report from that artifact. See the [generation prefill reporting
implementation plan](2026-07-31-full-run-timing-and-prefill.md) for the
formulas, evidence rules, report mapping, and artifact rebuild procedure.

## Excluded runs

This sweep does not include:

- other context lengths.
- other concurrency values.
- prefill-only measurements.
- maximum-throughput reference workloads.
- prefix-cache measurements.
- stress extensions.
- speculative decoding unless the deployment being measured explicitly includes it.

A run outside this fixed grid belongs to another sweep or a diagnostic artifact. Do not include it in the practical c1/c6 64k comparison.
